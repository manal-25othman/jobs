# خطة بيئة التجربة الخاصة (Staging) لنَقْلة

> **الحالة:** جاهزة للتنفيذ **بعد موافقتك وإنشائك الحسابات**. لم يُنشأ أي حساب ولم يُنشر شيء.
> - **الأسعار والحدود:** من الصفحات الرسمية، قُرئت في 2026-11-27 (`docs/ops/research/INFRA-ISOLATION-MODELS-RESEARCH.md`).
> - **البيانات:** اصطناعية فقط في Staging. لا تسجيل عام. لا Production الآن.

## 1. تقرير الجاهزية

| المكوّن | جاهز للنشر؟ | ما عُدِّل في هذه المرحلة | ما يبقى |
|---|---|---|---|
| تطبيق الخرّيج (Next.js) | نعم | `apps/app/vercel.json` للمستودع الأحادي؛ قفل Basic Auth للبيئة الخاصة (`middleware.ts`)؛ `robots.txt` يمنع الفهرسة؛ رؤوس أمان | ضبط المتغيرات في Vercel |
| الخادم (NestJS) | نعم | صورة Docker مصحَّحة (مساحات العمل، والبيانات، وفحص الصحة، ومسار التشغيل)؛ `PORT` من المضيف؛ trust proxy؛ **تحديد معدل الطلبات**؛ رؤوس أمان؛ **قائمة المدعوّين** في Staging؛ `NAQLA_ENV` | البناء الفعلي في CI (وظيفة `docker`) |
| قاعدة البيانات | نعم | 44 ترحيلًا تعمل على Postgres المجرّد وعلى Supabase (أدوار `auth` تُنشأ فقط عند غيابها)؛ سكربت إعداد يسجّل الترحيلات المطبَّقة | التطبيق على مشروع Staging |
| المصادقة | نعم | Supabase Auth موجود (JWT يتحقق منه الخادم) | **تحقق مطلوب:** المشاريع الجديدة في Supabase قد تستخدم مفاتيح توقيع غير متماثلة؛ الخادم يدعم اليوم السر المشترك (HS256) فقط (§9) |
| التخزين | نعم | محوّل Supabase Storage موجود؛ الذاكرة مرفوضة على المضيف | إنشاء الدلاء الخاصة |
| GitHub | محاكاة الآن | تكامل حقيقي جاهز (`GITHUB_MODE=app`) ومختبَر على خادم وهمي فقط | إنشاء تطبيق GitHub للتجربة بعد موافقتك |
| الاختبارات الآلية R2 | **لا تعمل على المضيف أبدًا** | وضع `recorded`: نتائج مسجّلة مسبقًا لنسخ المستودعات المحاكاة، موسومة | مضيف R2 مستقل بعد المراجعة الأمنية |
| الوكلاء | مزوّد الاختبار | — | النموذج الحقيقي بعد `OPEN-023` |
| محتوى التجربة | **يحتاج قرارك** | قرار D-136 يقصر نشر محتوى التجربة على الجهاز المحلي. أُضيف مسار للبيئة الخاصة **مقفل** إلا برقم قرار منكِ (`PILOT_STAGING_DECISION`) | قرارك (§8، البند 2) |

## 2. مخطط البنية

```
             ┌──────────── متصفح المختبِر (جوال / كمبيوتر) ────────────┐
             │                                                          │
   قفل 1: Basic Auth (Vercel env)                         رابط الدخول بالبريد (Supabase Auth، دعوات فقط)
             ▼                                                          ▼
   Vercel (Hobby) ─ Next.js ── HTTPS ──▶ Railway (Hobby) ─ NestJS API (Docker)
   apps/app                              • قفل 2: قائمة المدعوّين STAGING_ALLOWED_EMAILS
                                         • CORS على عنوان Vercel فقط، وتحديد معدل الطلبات، ورؤوس أمان
                                         • GitHub: محاكاة (أو تطبيق تجربة لاحقًا)، وR2: نتائج مسجّلة
                                                   │ (اتصال Postgres مشفّر)
                                                   ▼
                                         Supabase (منطقة Frankfurt) ─ Postgres + Auth + Storage
                                         • RLS، والأدوار، والدلاء الخاصة، والبيانات الاصطناعية

   خارج هذا المخطط عمدًا: مشغّل R2 (لا يعمل على Railway ولا Vercel)، والنماذج الحقيقية، وProduction.
```

**موطن البيانات:**
- لا منطقة شرق أوسطية لدى Supabase ولا Vercel ولا Railway، بحسب صفحاتها الرسمية.
- لذلك Staging في أوروبا، **ببيانات اصطناعية فقط**، وهذا يتفق مع توصية G1 للتجريب.
- خيارات الإنتاج داخل المملكة في §7.

## 3. الخدمات والتكلفة الشهرية (Staging)

| الخدمة | الخطة المقترحة | السعر الرسمي | حدود مهمة | لماذا |
|---|---|---|---|---|
| Supabase | **Free** | 0$ | مشروعان نشطان؛ **يتوقف المشروع بعد أسبوع بلا نشاط**؛ 500 MB قاعدة بيانات؛ **لا نسخ احتياطية تلقائية**؛ SMTP مخصّص متاح؛ إيقاف التسجيل العام متاح | يكفي لتجربة أسبوعين ببيانات اصطناعية. البديل Pro بـ25$ شهريًا (نسخ يومية 7 أيام) |
| Vercel | **Hobby** | 0$ | لا Password Protection (هي في Pro بـ20$ للمشروع)؛ Vercel Authentication بمستخدم خارجي واحد فقط على Hobby. **شرط الاستخدام التجاري على Hobby غير متحقَّق منه** | القفل يأتي من Basic Auth في التطبيق ومن قائمة المدعوّين |
| Railway | **Hobby** | 5$ حدًّا أدنى، تشمل 5$ استخدامًا | فحص الصحة عند النشر فقط (ليس مراقبة مستمرة)؛ متغيرات «مختومة» لا تُقرأ بعد حفظها؛ مناطق US/EU/سنغافورة | الأبسط لصورة Docker |
| GitHub | Free (مستودع خاص) | 0$ | Actions من 12$ رصيدًا مجانيًا شهريًا («2,000 دقيقة»)، وتتوقف عند النفاد دون وسيلة دفع؛ **لا Secret scanning للمستودعات الخاصة في Free** | CI قائم |

**المجموع المتوقع:**
- **نحو 5$ شهريًا**، أو 30$ إن اخترتِ Supabase Pro للنسخ الاحتياطي.
- لا نموذج حقيقي، ولا خدمة مراقبة مدفوعة.

**تقدير استهلاك Railway:**
- الأسعار الرسمية: الذاكرة 0.00000386$ لكل GB في الثانية، والمعالج 0.00000772$ لكل vCPU في الثانية.
- خادم بـ0.5 GB ذاكرة يعمل الشهر كاملًا: نحو 5$ للذاكرة. استهلاك المعالج في تجربة صغيرة ضئيل.
- **قد يتجاوز** الرصيد المشمول قليلًا. يمكن خفضه بإيقاف الخادم خارج أوقات التجربة.

## 4. متغيرات البيئة (بلا قيم سرية)

أين تُضاف: **في خزائن المتغيرات في كل خدمة**، لا في المستودع ولا في المحادثة. السر يُلصق مرة واحدة في حقله، ويُختم في Railway.

**Railway، خدمة API:**

|---|---|---|
| `NODE_ENV` | `production` | لا |
| `NAQLA_ENV` | `staging` | لا |
| `NAQLA_DEPLOY_REGION` | منطقة Supabase المختارة (مثل `eu-central-1`) | لا |
| `DATABASE_URL` | رابط Postgres من Supabase (Connection string) | **نعم** |
| `SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_URL` | عنوان المشروع | لا |
| `SUPABASE_SERVICE_ROLE_KEY` | من إعدادات API في Supabase | **نعم** |
| `SUPABASE_JWT_SECRET` | من إعدادات JWT في Supabase (§9) | **نعم** |
| `STORAGE_DRIVER` | `supabase` | لا |
| `STORAGE_BUCKET_PREFIX` | `staging` | لا |
| `CORS_ALLOWED_ORIGINS` | عنوان تطبيق Vercel فقط | لا |
| `STAGING_ALLOWED_EMAILS` | بريدك وبريد المختبِرين، أو `@نطاق` | لا (لكنه خاص) |
| `RATE_LIMIT_PER_MINUTE` | `120` | لا |
| `AGENT_PROVIDER` | `local-test` | لا |

| `LEARNING_CANDIDATE_PREVIEW` | `internal` | لا |

| `GITHUB_APP_*` | عند تفعيل تطبيق GitHub (`docs/ops/GITHUB-APP-STAGING-SETUP.md`) | بعضها **نعم** |

**Vercel، المشروع `apps/app`:**

| المتغير | القيمة | سري؟ |

## 5. خطة قاعدة البيانات

1. **مشروع Supabase جديد خاص بـStaging.** لا يُستخدم «بديهة» ولا أي مشروع آخر. المنطقة: Frankfurt (`eu-central-1`)، وهي **لا تُغيَّر بعد الإنشاء**.
2. **الترحيلات:**
   - `node scripts/staging/setup-staging.mjs --step migrate` يطبّق 44 ترحيلًا والبيانات الأولية بالترتيب، ويسجّل كل ملف في `naqla_migration`، فالإعادة آمنة.
   - التراجع: ملفات `supabase/rollback/*.down.sql`، وكلها ترفض الحذف إن وُجدت بيانات.
3. **البيانات:** `--step data` يستورد بيانات المسار ثم محتوى التجربة الموسوم: المواد، والموارد، وسيناريوهات المدير.
4. **الحسابات:**
   - `--step accounts --testers <ملف خارج المستودع>` ينشئ المدعوّين في Supabase Auth **بلا كلمة مرور** (الدخول برابط البريد).
   - ثم يمنح الأدوار: `human_reviewer`، و`sme`، و`track_admin`، و`product_owner`. الخرّيج لا يحتاج دورًا.
5. **النشر:** `--step publish` لا يعمل إلا بعد قرارك (`PILOT_STAGING_DECISION`).
6. **RLS والعزل:** بعد الإعداد يُشغَّل `npm run live:supabase`، وهو قائم سابقًا. يثبت على المشروع الحقيقي جلسات Supabase، وRLS بالأدوار الحقيقية، والتخزين الخاص بروابط موقّعة، وإلغاء رابط المشاركة.
7. **النسخ الاحتياطي والاستعادة:**
   - **Free:** تصدير يدوي بـ`pg_dump` قبل كل تغيير كبير، كما يوصي Supabase لمشاريع Free.
   - **Pro:** نسخ يومية 7 أيام.
   - **اختبار الاستعادة:** على مشروع ثانٍ قبل نهاية الأسبوع الأول.

## 6. خطة حماية بيئة التجربة

| الطبقة | الضابط |
|---|---|
| الوصول للواجهة | Basic Auth على كل صفحة، ومتغيراته في Vercel فقط؛ ومنع الفهرسة |
| تسجيل الدخول | **إيقاف التسجيل العام في Supabase** (Allow new users to sign up = off)؛ المدعوّون فقط |
| الخادم | قائمة المدعوّين `STAGING_ALLOWED_EMAILS` ترفض أي جلسة لغيرهم (403)؛ CORS على عنوان التطبيق فقط؛ 120 طلبًا في الدقيقة لكل عميل |
| البيانات | اصطناعية فقط، وكل محتوى التجربة موسوم «تجريبي» |
| الكود غير الموثوق | لا يُشغَّل على Railway ولا Vercel أبدًا؛ R2 بنتائج مسجّلة فقط |
| الأسرار | في خزائن الخدمات فقط، ومختومة في Railway. **لا تُرسل في المحادثة.** إلغاؤها: تدوير المفتاح في Supabase، ثم تحديث المتغير |
| المراقبة | سجلات Railway (7 أيام في Hobby)؛ فحص صحة `/health` عند النشر. لا مراقبة مستمرة مجانية من Railway، فيُقترح فحص خارجي لاحقًا |

## 7. موطن البيانات للإنتاج (للقرار لاحقًا، لا الآن)
- **Google Cloud:** منطقة الدمام (`me-central2`) مذكورة رسميًا، وشروط الوصول إليها في وثيقة لم تُقرأ بعد.
- **AWS:** المنطقة السعودية «معلَنة» وغير متاحة حاليًا.
- **Azure:** تذكر «Saudi Arabia East» ضمن المناطق «المتاحة أو القادمة».
- **الأثر:** إنتاج داخل المملكة يعني على الأرجح استضافة الخادم وقاعدة البيانات خارج Supabase وRailway، مثل Postgres مُدار على Google Cloud الدمام، والقرار في G1.

## 8. الخطوات المطلوبة منكِ بالترتيب
1. **جعل المستودع خاصًا** (`docs/ops/REPO-PRIVACY-AUDIT.md` §6).
2. **قرار:** السماح بنشر محتوى التجربة الموسوم في بيئة التجربة الخاصة فقط (تمديد D-136)، أو لا. دونه تعمل البيئة لكن بلا أنشطة منشورة.
3. **Supabase:**
   - أنشئي حسابًا ثم مشروعًا جديدًا باسم `naqla-staging`، منطقة Frankfurt، وكلمة مرور قاعدة بيانات قوية تحفظينها في مدير كلمات المرور.
   - Authentication → Providers → Email: أوقفي «Allow new users to sign up».
   - Settings → API و Database: انسخي القيم إلى خزائن Railway وVercel مباشرة (§4).
4. **Railway:**
   - أنشئي حسابًا، ثم مشروعًا من مستودع GitHub الخاص (امنحي الوصول لهذا المستودع وحده)، وخدمة باسم `api`.
   - في الإعدادات: Config-as-code path = `ops/railway/api.railway.json`.
   - أضيفي المتغيرات (§4) واختمي الأسرار.
5. **Vercel:**
   - أنشئي حسابًا، ثم استوردي المستودع الخاص، وRoot Directory = `apps/app`.
   - أضيفي المتغيرات (§4)، ومنها بيانات Basic Auth.
6. **الإعداد الأولي:** إما أن تشغّليه أنتِ من جهازك بالأوامر في §5 مع المتغيرات في الطرفية، أو تمنحيني الإذن بخطوة محددة.
7. **ملف المختبِرين:** بريدك وبريد المختبِرين والأدوار، **في ملف على جهازك خارج المستودع**.
8. بعد ذلك أُجري اختبار ما بعد النشر (§10)، ثم أعطيك الرابط.

## 9. نقطة تحقق تقنية قبل الربط
- الخادم يتحقق من رموز Supabase بالسر المشترك (HS256، `SUPABASE_JWT_SECRET`).
- مشاريع Supabase الأحدث قد تصدر رموزًا بمفاتيح توقيع غير متماثلة. **لم أتحقق من ذلك في الصفحات الرسمية.**
- إن كان المشروع الجديد كذلك، يلزم دعم JWKS في الحارس. التعديل صغير، ويُختبر على المشروع نفسه.
