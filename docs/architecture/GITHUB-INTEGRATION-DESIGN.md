# تصميم التكامل مع GitHub: المعمارية والأمن والصلاحيات والتكلفة

> **الحالة:** تصميم معروض قبل التفعيل الحقيقي (قرار المالكة 1، الجولة 2 من المرحلة ج).
> - **المنفَّذ الآن:** العقود، والواجهات، ومزوّد محاكاة للاختبار (`GITHUB_MODE=simulated`)، وهو مرفوض في الإنتاج.
> - **لم يُنشأ** تطبيق GitHub حقيقي، ولم تُطلب أي صلاحية فعلية، ولم يُرسل أي طلب إلى GitHub.
> - **المصدر:** صفحات GitHub الرسمية، قُرئت في 2026-11-26. السجل والاقتباسات في `docs/ops/research/GITHUB-APP-INTEGRATION-RESEARCH.md`، وما لم يُتحقق منه موسوم **UNVERIFIED**.

## 1. لماذا GitHub App

| الخيار | الصلاحيات | اختيار المستودعات | الرموز | الحكم |
|---|---|---|---|---|
| **GitHub App** | دقيقة؛ «Contents: read» ممكنة وحدها | المثبِّت يختار «Only select repositories» ويغيّرها لاحقًا | رمز التثبيت ينتهي بعد ساعة، ويمكن تضييقه لمستودعات وصلاحيات محددة | **المختار** |
| OAuth App | نطاقات واسعة مثل `repo` تسمح بتعديل المحتوى والإعدادات | لا اختيار للمستودعات | رمز طويل العمر | مرفوض: يخالف «الحد الأدنى من الصلاحيات» |
| رمز وصول شخصي | ينشئه المستخدم يدويًا | — | GitHub يقول إن التطبيقات «should never use a personal access token» | مرفوض |

**حقيقة موثَّقة مهمة:** لأي GitHub App «دائمًا قراءة على كل المستودعات العامة». لذلك **المنصة نفسها** تقصر القراءة على ما اختاره الخرّيج:
- `assertRepositoryUsable` يرفض أي مستودع غير مسجَّل في `github_link_repo`.
- لا يوجد في الكود طريق يقرأ مستودعًا بالاسم فقط.

## 2. الصلاحيات المطلوبة (قراءة فقط)

| الصلاحية | المستوى | ما تتيحه (من التوثيق) | لماذا |
|---|---|---|---|
| Contents | read | الأرشيف عند إيداع (tarball/zipball)، والإيداعات، والمقارنة، والفروع | قراءة الكود عند الإيداع المثبَّت، وتاريخ العمل |
| Pull requests | read | طلب الدمج وإيداعاته وملفاته | التحقق من أن رأس طلب الدمج هو الإيداع المعلَن، وقراءة الوصف |
| Metadata | read | البيانات الوصفية للمستودع | الاسم والخصوصية والفرع الافتراضي. كونها إلزامية تلقائيًا **UNVERIFIED** |

- **لا يُطلب أبدًا:** أي `write` أو `admin`، ولا Workflows، ولا Administration، ولا Secrets.
- هذا مفروض في الكود: `assertReadOnlyPermissions` يرفض أي صلاحية خارج القائمة أو بمستوى غير `read`، ويُتحقق منه عند كل ربط.

## 3. رحلة الخرّيج

1. **الربط:** «ربط GitHub» → صفحة تثبيت التطبيق على GitHub → الخرّيج يختار المستودعات → عودة إلى نَقْلة.
   - تُسجَّل الصلة والمستودعات المختارة فقط.
   - **لا يُشترط إنشاء منظمة.** التثبيت على الحساب الشخصي موثَّق.
2. **اختيار ما يُسلَّم:** في مكان العمل يختار الخرّيج المستودع، ثم طلب الدمج (برأسه) أو إيداعًا بعينه.
3. **التسليم من المستودع:**
   - تُجلب ملفات الإيداع المثبَّت وتصبح مخرجات النشاط: `index.html` ← `file.index_html`، وهكذا.
   - يُضاف رمز الإيداع ورابط طلب الدمج.
   - قواعد التسليم المعتادة كما هي، ويُسجَّل التثبيت في `submission_source` ولا يتغيّر بعدها.
4. **النتائج:** تُشغَّل اختبارات النشاط على هذا الإيداع نفسه (R2، وضع الظل)، ثم التقييم المعتاد والمراجعة البشرية.
5. **الإصلاح وإعادة التسليم:** يصلح الخرّيج بنفسه ويدفع إيداعًا جديدًا ويسلّم مرة أخرى. كل محاولة تحتفظ بإيداعها ونتائجها (`/projects/:id/attempts`).
6. **إلغاء الربط:** من نَقْلة، أو بإزالة التطبيق من GitHub.
   - القراءة تتوقف فورًا.
   - الأدلة المثبَّتة السابقة تبقى تاريخًا، فلا تُمحى نتيجة قُيّمت.

## 4. البنية

```
الخرّيج ──(تثبيت على مستودعات مختارة)──▶ GitHub
   │                                        │ webhooks موقّعة (installation / installation_repositories / github_app_authorization)
   ▼                                        ▼
تطبيق نَقْلة ─▶ API (GitHubService) ─▶ GitHubPort ─▶ [محاكاة الآن | محوّل GitHub App بعد الموافقة]
                      │                     └─ لكل قراءة: رمز تثبيت قصير مُضيَّق لمستودع واحد وقراءة فقط، لا يُحفظ
                      ├─ github_link / github_link_repo / submission_source (بلا أعمدة رموز)
                      ├─ TestRunService ─▶ apps/runner (R2، عملية منفصلة، بلا شبكة ولا قاعدة بيانات)
                      └─ A13 / A15 (ملاحظات Git ونتائج الاختبارات، نصوص المستودع بيانات غير موثوقة)
```

## 5. الأمن

| الخطر | الضابط | الحالة |
|---|---|---|
| صلاحيات زائدة | قائمة قراءة فقط مفروضة في الكود، وتُتحقق عند الربط | منفَّذ |
| قراءة مستودع لم يُختر (والتطبيق يرى كل المستودعات العامة) | القراءة فقط مما في `github_link_repo`، ومستودع غير مملوك للخرّيج مرفوض | منفَّذ |
| تسريب رموز الوصول | **لا يُخزَّن أي رمز**: رمز تثبيت لكل عملية ينتهي خلال ساعة. إثبات قاعدة البيانات يتحقق من عدم وجود أعمدة رموز أو أسرار | منفَّذ |
| تسريب المفتاح الخاص للتطبيق | خزنة مفاتيح بالتوقيع فقط، لا في المستودع ولا في متغيرات عادية، كما يوصي GitHub | للتفعيل الحقيقي |
| تزوير webhook | HMAC-SHA256 على الجسم الخام مع مقارنة ثابتة الزمن، وسرّ بطول 32 حرفًا على الأقل، والرد خلال 10 ثوانٍ | منفَّذ ومختبَر |
| إعادة إرسال webhook | `X-GitHub-Delivery` يُسجَّل ويُرفض تكراره | منفَّذ |
| تغيير الكود بعد التسليم | التثبيت على رمز إيداع كامل، و`snapshot_hash` لما جُلب، وجدول لا يُعدَّل | منفَّذ |
| طلب دمج رأسه غير المعلَن | `assertPinMatchesPullRequest` يرفض | منفَّذ |
| حقن تعليمات للوكلاء في رسائل الإيداع أو الوصف أو التعليقات | كل نص من المستودع يمر بـ`asUntrustedRepoText`: حذف المحارف الخفية، وقطع الطول، ووسم «مشتبه» للمراجِع. الوكلاء يقرؤونه بيانات لا تعليمات، وحارس A13 يرفض لغة القرار | منفَّذ |
| كشف مستودع خاص أو بيانات الخرّيج | RLS: المالك وحده، والمراجِع المكلَّف عبر الخدمة فقط. لا عرض عام | منفَّذ |
| سحب الصلاحية | إلغاء الربط من نَقْلة؛ وwebhooks الإزالة وإلغاء التفويض تُلغي القراءة، ويُسجَّل السبب | منفَّذ |
| المستودع العام وحده لا يكفي دليلًا | التقييم على الإيداع المثبَّت، والأعداد ملاحظات للمراجِع فقط | منفَّذ |

## 6. متى يكون GitHub إلزاميًا (`githubRequirementFor`)

| النشاط | GitHub |
|---|---|
| يقيس Git وسير العمل (معيار `git_workflow`، أو مخرج إلزامي `link.pull_request` / `text.head_sha`) | **إلزامي** |
| نشاط برمجي آخر | اختياري (رفع ملفات أو GitHub) |
| مسار غير برمجي | **لا يُعرض** |

## 7. التكلفة

| البند | التكلفة | المصدر |
|---|---|---|
| تسجيل GitHub App واستخدامه | لا تذكر الصفحات الرسمية المقروءة أي رسوم؛ **UNVERIFIED** (صفحة الأسعار أعادت 403) | البحث، س9 |
| حدود الطلبات | 5,000 طلب في الساعة لكل تثبيت، و+50 لكل مستودع فوق 20، بحد أقصى 12,500. يكفي بفارق كبير: نحو 5–10 طلبات لكل تسليم | البحث، س8 |
| التخزين | لقطة نصية لكل تسليم (عشرات الكيلوبايتات) | تقدير |
| Marketplace | غير مطلوب للتوزيع | البحث، س9 |

## 8. ما يحتاج موافقتك قبل التفعيل الحقيقي
1. إنشاء تطبيق GitHub باسم نَقْلة بالصلاحيات الثلاث أعلاه للقراءة فقط، ونقطة webhook، وخزنة للمفتاح الخاص.
2. المنطقة والاستضافة (G1) وقرار الخصوصية (G2)، لأن الكود المجلوب بيانات شخصية للخرّيج.
3. محوّل `GitHubPort` الحقيقي: يُكتب بعد الموافقة، ويُختبر على مستودعات اصطناعية أولًا.
