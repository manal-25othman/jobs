## 2. التوصية

1. **الآن، لحجم نَقْلة الحالي (تجربة، ومئات المحاولات شهريًا):**
   - **gVisor على آلة افتراضية مخصّصة وصغيرة**، منفصلة تمامًا عن الخادم وقاعدة البيانات.
   - يشغّل المشغّل الحالي (`apps/runner`) مع استبدال واجهة `namespace-dev` بواجهة `gvisor`. المتصفح والاختبارات تبقى كما هي، والتحقق خارج الصندوق كما هو.
   - **لماذا:** عزل حقيقي للنواة دون متطلب KVM، وتكلفة آلة واحدة، وممكن داخل المملكة، والبيانات لا تخرج إلى طرف ثالث.
2. **عند التوسع** (آلاف المحاولات يوميًا، أو سياسة أمنية أشد):
   - **Firecracker** على خادم فعلي في المنطقة نفسها، بآلة افتراضية لكل محاولة.
   - أو **Cloud Run في الدمام** إن ثبتت شروط الوصول وناسبت الخصوصية (G2).
3. **غير موصى به لهذا الغرض:**
   - e2b وLambda: بيانات الخرّيج تخرج إلى طرف ثالث، والمنطقة غير متحقَّقة أو غير متاحة.
   - أي تشغيل على Railway أو Vercel أو خادم NestJS.

## 3. ما يُبنى قبل التشغيل الحقيقي (بعد موافقتك)
- **واجهة `gvisor` في المشغّل:**
  - `runsc --network=none` مع cgroups للمضيف؛
  - صورة جذر للقراءة فقط فيها Chromium وNode مثبتين؛
  - قرص مؤقت لكل محاولة، وحذف بعد الانتهاء.
- **عامل R2 كخدمة منفصلة:**
  - يستقبل لقطة الكود ومعرّف الحزمة عبر اتصال خاص موقّع (HMAC) من الخادم، ويعيد النتيجة فقط؛
  - لا قاعدة بيانات، ولا أسرار، ولا وصول للإنترنت؛
  - يضاف إلى الخادم وضع `R2_MODE=remote`.
- **سجل تدقيق** لكل محاولة: رمز الإيداع، وتجزئة اللقطة، والحدود، والمدة.
