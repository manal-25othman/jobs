# Career OS — Architecture Foundations (v0.1)
> **مستوى هذه الوثيقة: معماري منطقي، محايد تقنيًا.** لا Stack، لا قاعدة بيانات محددة، لا Schema نهائي، لا UI.
> **هدفها الوحيد:** أن يكون كل عنصر مؤجّل في سجل الرؤية **قابلًا للفتح لاحقًا بتكلفة إضافة، لا بتكلفة إعادة بناء**.

## السؤال المعماري الحاكم
> ما القرارات التي إن أخطأناها في Phase 1 **أجبرتنا على الهدم لاحقًا**؟
نبني هذه فقط بعمق، ونبقي كل ما عداها رقيقًا أو قابلًا للرمي.

**قاعدة الفصل:** نميّز بصرامة بين **النواة الدائمة** (تُبنى مرة، تتغير ببطء شديد) و**الطبقة الاستهلاكية** (يُتوقع رميها وإعادة كتابتها مرارًا، وهذا مقصود).

## 1. الطبقات (Layered View)

```
L9  الحوكمة والامتثال    Provenance · Consent · Audit · Cost Ledger      [نواة — P1]
L8  الإشارات             Signal Bus (تنبيهات، تذكيرات، محفّزات)          [نواة رقيقة — P1]
L7  الإسقاطات            CV · LinkedIn · Portfolio · Case Study · Site   [استهلاكية]
L6  زمن تشغيل الوكلاء     Agent Contracts · AI Gateway · Guardrails       [نواة — P1]
L5  التقييم              Rubric-as-Data · Evaluator Plugins              [نواة — P1]
L4  التنفيذ              Journey Engine · Activity Runtime               [نواة — P1]
L3  المحتوى والتصنيف      Skill Ontology · Role Specs · Activity Specs    [محتوى — يتوسع بلا كود]
L2  سجل الأحداث          Career Event Log (append-only)                  [نواة — P1]
L1  الرسم المهني          Career Graph (مصدر الحقيقة)                     [نواة — P1]
L0  الهوية والاستئجار     User · Org (محجوز) · Consent                    [نواة — P1]
```

**قاعدة الاتجاه:** الاعتماد يتجه لأسفل دائمًا. لا تعرف L1 شيئًا عن L7، ولا يكتب L6 في L1 مباشرة أبدًا.

## 2. القرارات الحاملة (Load-Bearing Decisions)

> 12 قرارًا فقط. كلها في Phase 1. كل واحد منها: **رخيص الآن، باهظ لاحقًا.**

### LBD-01 — الرسم المهني هو مصدر الحقيقة الوحيد (Career Graph)
**القرار:** كيانات مفاهيمية أساسية (غير نهائية): `Person` · `Claim` (ادعاء مهارة/قدرة) · `Evidence` (دليل) · `WorkItem` (وحدة عمل) · `Activity` (نشاط مُصمَّم) · `Submission` · `Evaluation` · `Achievement` · `Gap` · `Goal`.
الرابط الجوهري: **`Claim` لا يوجد بلا `Evidence` واحد على الأقل، و`Evidence` لا يوجد بلا `Submission` أو مصدر موثّق.**
**ماذا يفتح:** CV وLinkedIn وPortfolio والموقع الشخصي والمطابقة — كلها قراءات من هذا الرسم.
**كلفة التأجيل:** كارثية. بناء CV ببيانات منفصلة ثم محاولة توحيدها لاحقًا = هجرة بيانات + فقدان أدلة + انهيار قاعدة "لا مهارة بلا دليل".

### LBD-02 — سجل أحداث غير قابل للتعديل (Career Event Log)
**القرار:** كل فعل ذي معنى يُكتب كحدث لا يُحذف ولا يُعدّل: `diagnosis.completed` · `activity.started` · `submission.received` · `evaluation.completed` · `evidence.created` · `asset.exported` …
**ماذا يفتح:** Achievement Engine · Smart Notifications · Companion Agent · تحليلات المنتج · إعادة حساب الخطط · تدقيق التقييم.
**كلفة التأجيل:** عالية جدًا — لا يمكن استرجاع أحداث لم تُسجَّل. كل ميزة مستقبلية تعتمد على "ماذا فعل المستخدم ومتى" تصبح مستحيلة أثريًا.
**حجم التنفيذ في P1:** بسيط جدًا (جدول أحداث + ناشر). الثمن كله في **الانضباط**، لا في الهندسة.

### LBD-03 — النشاط الموحّد (Unified Activity Spec) — **أهم قرار لمنع إعادة البناء**
**القرار:** المهمة والمحاكاة والمقابلة وتحدي Career Gym ومشروع المستخدم ليست أنواعًا مختلفة، بل **`Activity` واحد بملفات تعريف (profiles) مختلفة**:
`mission` (P1) · `project` (P2) · `simulation` (P3) · `interview` (P3) · `micro_challenge` (P4–P5) · `business_exercise` (P5).
كل Activity Spec = ملف محتوى مُصدَّر يحوي: السياق، الأدوار غير البشرية، المدخلات/الملفات، المخرجات المتوقعة، الأحداث المُقحَمة (تغيّر متطلبات، معلومة ناقصة)، الرُبريك، المهارات المستهدفة.
**ماذا يفتح:** C06 · C14 · C17 · C16 — أربعة مكوّنات كبرى تصبح **محتوى لا كود**.
**كلفة التأجيل:** كارثية. بناء "محرك مهام" ثم "محرك محاكاة" ثم "محرك مقابلات" منفصلين = ثلاثة أنظمة تقييم وثلاثة أنظمة أدلة وثلاث فواتير صيانة.
**حجم التنفيذ في P1:** نصمّم المخطط كاملًا، وننفّذ ملف `mission` فقط.

### LBD-04 — الرُبريك بيانات مُصدَّرة، والمقيّمون إضافات (Rubric-as-Data + Evaluator Plugins)
**القرار:** الرُبريك كيان مُصدَّر (versioned) خارج الكود وخارج الـprompt. والتقييم خط أنابيب من مقيّمين مستقلين: `rule_based` → `rubric_llm` → `behavioral` (P3) → `human_review` (P1 خلفيًا).
كل `Evaluation` تحفظ: `rubric_version` · `evaluator_chain` · درجة كل بند · المبرر · المقتطف الداعم.
**ماذا يفتح:** التقييم السلوكي، مراجعة الخبراء، المعايرة، قياس الاتفاق، والتقاضي عند اعتراض المستخدم.
**كلفة التأجيل:** عالية — تقييمات بلا إصدار رُبريك = بيانات لا تصلح للمعايرة، وأدلة لا يمكن الدفاع عنها.

### LBD-05 — الوكلاء يقترحون ولا يكتبون (Proposal-Only Agents)
**القرار:** **لا وكيل يكتب في Career Graph مباشرة.** كل وكيل يُخرج `Proposal` مُنمَّطًا يمر عبر بوابة التحقق (L9) التي تفرض: وجود دليل، عدم التناقض، عدم المبالغة، عدم الاختلاق، وجود رُبريك للدرجات.
**ماذا يفتح:** إضافة أي وكيل من الـ19 لاحقًا بلا مخاطرة على سلامة البيانات؛ وQuality & Verification Agent (A18) يترقّى من قواعد إلى وكيل بلا تغيير في العقد.
**كلفة التأجيل:** كارثية على المصداقية — سماح واحد بالكتابة المباشرة يُفسد سجل الأدلة بلا رجعة.

### LBD-06 — المنسّق آلة حالات أولًا (Journey Engine)
**القرار:** Orchestrator في P1 = **رحلات مُعرَّفة بشكل حتمي** (Journey = خطوات، شروط، مخرجات، سقف تكلفة). الوكلاء خطوات داخلها. التوجيه الديناميكي يُضاف لاحقًا **كسياسة داخل نفس المحرك**، لا كنظام بديل.
**ماذا يفتح:** منع الحلقات اللانهائية، ضبط أي وكيل يعمل ومتى، تشغيل انتقائي للوكلاء، والتحكم في التكلفة — وهي مطالب صريحة في الرؤية.
**كلفة التأجيل:** متوسطة-عالية. البدء بوكيل حر يعني سلوكًا غير قابل للتكرار وفاتورة غير متوقعة، ثم إعادة كتابة كاملة عند التحكم.

### LBD-07 — بوابة الذكاء الاصطناعي (AI Gateway) منذ اليوم الأول
**القرار:** كل استدعاء نموذج يمر عبر بوابة واحدة تُسجّل: الوكيل، الرحلة، المستخدم، النموذج، إصدار الـprompt، التوكنات، الكلفة، زمن الاستجابة، والتخزين المؤقت. وتفرض: توجيه النموذج حسب المهمة، وسقوفًا للميزانية.
**ماذا يفتح:** cost per user · cost per simulation · token tracking · agent usage · model routing · caching · budget limits — كلها مطالب صريحة، وكلها تصبح **إعدادات** لا مشاريع.
**كلفة التأجيل:** عالية جدًا. لا يمكن استرجاع تكلفة لم تُقَس، ولا يمكن تسعير منتج لا نعرف كلفته.
**حجم التنفيذ في P1:** صغير (طبقة اعتراض + جدول قياس). **لا يوجد مبرر لتأجيله.**

### LBD-08 — تصنيف مهارات داخلي بمحوّلات خارجية (Skill Ontology + Adapters)
**القرار:** معرّفات مهارات **داخلية دائمة** تملكها المنصة، وجدول مطابقة منفصل: `skill_id ↔ external_code (ESCO / التصنيف الوطني / غيرهما)`. في P1 يُملأ التصنيف الداخلي يدويًا لمسار واحد، وجدول المطابقة يبقى فارغًا.
**ماذا يفتح:** D01 · D02 · C15 — بتعبئة بيانات لا بهجرة.
**كلفة التأجيل:** عالية. ربط الأدلة مباشرة بأكواد مصدر خارجي = رهن المنتج بترخيص وبنية جهة خارجية، وإعادة ربط كل دليل عند تغييرها.

### LBD-09 — وسم المصدر إلزامي على كل حقيقة (Provenance)
**القرار:** كل حقيقة في النظام تحمل تصنيفًا إلزاميًا من أربعة: `authoritative` · `curated` · `ai_generated` · `user_evidence` — وهو مطلب صريح في الرؤية، ونجعله **حقلًا إلزاميًا لا حقلًا اختياريًا**.
**ماذا يفتح:** عرض "لماذا نقول هذا" للمستخدم · منع تقديم مخرج AI كحقيقة سوقية · تدقيق الجودة · الثقة لدى المشغّل.
**كلفة التأجيل:** عالية — وسم أثر رجعي لملايين الحقائق مستحيل عمليًا.

### LBD-10 — الأصول المهنية إسقاطات لا بيانات (Projections)
**القرار:** CV وLinkedIn وPortfolio وCase Study والموقع الشخصي = **عارضات (renderers) فوق Career Graph**، تُخزَّن كنسخ مُولَّدة قابلة لإعادة التوليد، ولا تملك حقيقة خاصة بها.
**ماذا يفتح:** C10 · C11 · C12 · C13 — كل واحد منها يصبح قالبًا جديدًا.
**كلفة التأجيل:** عالية. "مولّد CV" بجداوله الخاصة يصبح مصدر حقيقة موازيًا، فيتفرّع المنتج ويسهل معه الاختلاق.

### LBD-11 — بذرة الهوية والمؤسسة والمساحة العامة
**القرار:** (أ) `org_id` اختياري موجود على الكيانات الرئيسية من P1 وإن لم تُستخدم. (ب) `username` يُطلب ويُحجز عند التسجيل، ومسار `/u/{username}` **محجوز وغير منشور**. (ج) نموذج صلاحيات بسيط لكنه صريح (مالك البيانات، من يرى الدليل).
**ماذا يفتح:** B2B2C في P5 · C13 في P4 — بلا هجرة هوية ولا تصادم أسماء ولا كسر روابط.
**كلفة التأجيل:** متوسطة-عالية. إضافة الاستئجار بعد سنة = لمس كل استعلام في النظام.

### LBD-12 — الخصوصية والموافقة والتوطين منذ البداية
**القرار:** سجل موافقات صريح (ما جُمع، لماذا، هل يُستخدم في تحسين النماذج، وهل يُعرض علنًا)، وقرار مبكر بمكان تخزين البيانات، وتصميم يسمح بالحذف والتصدير. مع i18n وRTL في نموذج المحتوى (لا نصوص مضمّنة في الكود).
**ماذا يفتح:** الامتثال لـPDPL · الأسواق والشراكات المؤسسية · ثنائية اللغة في P2.
**كلفة التأجيل:** عالية وقانونية، لا تقنية فقط.

## 3. الثوابت المعمارية (Invariants) — تسري على كل المراحل

1. **لا `Claim` بلا `Evidence`.** (G01)
2. **لا `Evaluation` بلا `rubric_version` مُصدَّر.** (G02)
3. **لا وكيل يكتب في Career Graph — اقتراحات فقط تمر ببوابة.** (LBD-05)
4. **لا معلومة سوقية بلا مصدر مُوسّم.** (G03)
5. **كل حقيقة تحمل `provenance`.** (LBD-09)
6. **كل استدعاء نموذج يمر بالبوابة ويُقاس.** (LBD-07)
7. **كل `Activity` يشير إلى Spec مُصدَّر.** (LBD-03)
8. **كل فعل ذي معنى يُنشر كحدث.** (LBD-02)
9. **`Activity Score ≠ Skill Verification Level`** — درجة النشاط لا تمنح مستوى مهارة تلقائيًا. (D-016)

> هذه التسعة **شروط قبول على كل Pull Request**، لا مبادئ إرشادية. خرقها يُعيد بناء المصداقية من الصفر.

## 5. ما يُسمح برميه عمدًا (Disposable by Design)

حتى لا نفرط في الهندسة، نُعلن صراحة ما **نتوقع إعادة كتابته** ولا نستثمر فيه:
- كل واجهات المستخدم في P1.
- كل نصوص الـprompt وصياغاتها (مُصدَّرة، لكن مُتوقَّع تغيّرها أسبوعيًا).
- خريطة المهارات اليدوية لـP1.
- الاستدلالات الأولية للتشخيص واختيار الموارد.
- قوالب الـCase Study والـCV الأولى.
- المراجعة البشرية الخلفية لأول 100 تسليم (آلية معايرة مؤقتة بطبيعتها).

**القاعدة:** نستثمر في **العقود والبيانات**، ونرمي **التنفيذ والصياغة**.

## 7. تعريف الإنجاز المعماري لـPhase 1

Phase 1 لا يُعتبر مكتملًا معماريًا إلا إذا:
- [ ] الثوابت التسعة مُطبَّقة وقابلة للفحص آليًا.
- [ ] مخطط `Activity Spec` مُصمَّم كاملًا ومُنفَّذ منه ملف `mission` فقط.
- [ ] الـ19 وكيلًا لهم **عقود مُعرَّفة** ولو كان تنفيذهم 4 وحدات.
- [ ] سجل الأحداث يستقبل كل أفعال الحلقة.
- [ ] بوابة الـAI تُخرج تقرير تكلفة لكل مستخدم ولكل رحلة.
- [ ] جدول مطابقة المهارات موجود وفارغ.
- [ ] `org_id` و`username` و`/u/{username}` محجوزة وغير مُفعّلة.
- [ ] سجل الموافقات يعمل، ومسارا التصدير والحذف موجودان.
- [ ] **اختبار التمديد:** إضافة رُبريك جديد + Activity جديد + قالب إسقاط جديد، بلا تعديل في النواة.

---

## 8. ما لم يُحسم بعد (ويُحسم في مرحلة Technical Design)

لا تُحسم هنا عمدًا، لأنها لا تؤثر على قابلية التمديد إن احتُرمت القرارات الحاملة:
لغة/إطار التنفيذ · نوع قاعدة البيانات · مزوّد الاستضافة والمنطقة · مزوّد النماذج · آلية التخزين المؤقت · نمط النشر · إطار الاختبارات.

**قاعدة:** لا نختار Stack قبل اعتماد هذه الأسس، ولا نبدأ Technical Design قبل اجتياز بوابة خروج Phase 0.

## 9. متطلب قابلية إضافة المسارات (ARCH-REQ-TRACK) *(D-027 · D-029 — ملزم)*

**ARCH-REQ-TRACK-01 — المسار معطى محتوى لا افتراض بنيوي.**
يُمنع على أي متطلب أو كيان أو عقد وكيل أو آلة حالات أو نموذج نشاط أو نموذج دليل أن يفترض مسارًا مهنيًا بعينه. `Data Analyst / BI` **مسار تحقق أول، وليس هوية المنتج**.

**ARCH-REQ-TRACK-02 — ما تعتمد عليه إضافة مسار جديد (محتوى وإعدادات فقط):**
`Role Definition` · `Skill Map` · `Activity Specs` · `Rubrics` · `Integrity Checks` · `Learning Resources` · `Content configuration`.

**ARCH-REQ-TRACK-03 — ما يُمنع تغييره لإضافة مسار:**
`Career Graph` · `Evidence model` · `Claim lifecycle` · `Evaluation pipeline` · `Agent orchestration contracts` · `Project/WorkItem model` · `CV/LinkedIn/Portfolio projection architecture`.

**ARCH-REQ-TRACK-04 — معيار الفشل:**
