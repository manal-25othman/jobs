## 1. ما هو Claude Ship (كما توثّقه المصادر)

| الوكيل | ما يفعله | الحالة |
|---|---|---|
| **Code Review** | يبحث عن «الأخطاء المنطقية، والثغرات الأمنية، وحالات الحافة المكسورة» (D1). ينشر ملاحظاته تعليقاتٍ على أسطر طلب الدمج، مرتّبة بثلاث درجات خطورة: Important وNit وPre-existing، مع ملخص وفحص `Claude Code Review` (D5, P2). **«يقرأ الفرق والكود المحيط دون بنائه أو تشغيله»** (D5). وحده لا يعتمد طلب الدمج ولا يمنعه (D5) | متاح عمومًا (GA) (D1) |
| **PR Steward** | «يدفع إيداعات لمعالجة ملاحظات المراجعة، ويحاول إصلاح الفحوص الفاشلة وتعارضات الدمج» دون أن يسأل أولًا (D4). لا يعتمد ولا يدمج (D1) | تجريبي عام (D1) |
| **Claude Approvals** | فحص يحدد «من بقي عليه أن يعتمد» وفق ملف سياسة `.claude/approvals.yml` في المستودع (D3). يمكن أن يعتمد Claude التغييرات الروتينية حيث تسمح السياسة (P1). يدعم مصنِّفات مخصّصة بتعليمات حرة (D6) | تجريبي عام (D1) |

- **التشغيل:** على بنية Anthropic، لا في CI ولا على خوادم ذاتية (D2, D5, D6).
- **المستودعات:** GitHub فقط؛ لا GitLab (P2).
- **الخطط:** Team وEnterprise فقط (P1, D1).
- **الفوترة:** حسب الاستخدام بالرموز، **بلا سعر ثابت للمراجعة** (D8)، مع سقوف إنفاق شهرية (P1, D8).
- **التوفر:** غير متاح مع Zero Data Retention، أو إعداد HIPAA، أو مفاتيح التشفير المُدارة من العميل (P1, D1).

## 2. هل يمكن دمجه مباشرة مع نَقْلة؟

**لا توجد واجهة برمجية موثّقة لذلك.** لا تذكر الصفحات الإحدى عشرة أي API أو SDK أو webhook يطلب مراجعة لكود خارج مستودع GitHub مربوط بتطبيق Claude. كل المحفّزات من جهة GitHub: فتح طلب الدمج، أو أمر `@claude review` في تعليق، أو وسم، أو أوامر في التعليقات (D5).

**الطريق الوحيد الممكن نظريًا:** أن تكون مستودعات الخرّيجين ضمن منظمة GitHub مربوطة بمؤسسة Claude من خطة Team أو Enterprise تملكها نَقْلة، وأن يُثبَّت فيها تطبيق Claude على GitHub. هذا يصطدم بما يلي:

| العائق | المصدر | الأثر على نَقْلة |
|---|---|---|
| **صلاحيات التطبيق واسعة، وتُقبل كاملة أو لا تُقبل.** القائمة: Actions، Checks، Contents، Discussions، Issues، Pull requests، Repository creation، Repository hooks، Workflows (قراءة وكتابة)، وAdministration، Members، Merge queues، Statuses، Dependabot alerts (قراءة). «GitHub لا يسمح بقبول جزء منها» | D7 | لا يجوز طلبها على مستودعات الخرّيجين الشخصية. قرار المالكة 5 يقصر الصلاحية على قراءة مؤقتة للمراجِع |
| التثبيت على مستوى المنظمة يحتاج **مالك منظمة GitHub** ومالك مؤسسة Claude | D2 | الخرّيج ليس مالكًا لمنظمة نَقْلة، والعكس |
| المراجعة **لا تشغّل الاختبارات** | D5 | لا تتحقق من سلوك العمل فعليًا |
| **PR Steward يكتب الكود بنفسه** | D4 | يخالف مبدأ «لا يُنفَّذ المشروع نيابة عن الخرّيج» مباشرة. يجب ألا يُفعَّل لأعمال الخرّيجين أبدًا |
| **Claude Approvals قد يمرّر طلب دمج دون موافقة أي إنسان** (`seats: 0`، أو `claude: approves`)، و«قد يعتمد تغييرًا لم يراجعه شيء» | D3, D9 | يخالف قاعدة نَقْلة: لا اعتماد مهني بلا إنسان، ولا تحقق من مهارة بقرار آلي |
| **المصنِّفات يمكن استدراجها بنص يكتبه صاحب طلب الدمج** | D6 | في سياق تقييمي، الخرّيج هو صاحب طلب الدمج؛ استدراج المقيِّم خطر نزاهة مباشر |
| لا جهة مساءلة مذكورة لاعتماد Claude | D9 | الاعتماد في نَقْلة مسؤولية مسمّاة: مراجِع بشري أو سياسة معتمدة |
| معالجة البيانات على بنية Anthropic، وغير متاح مع ZDR | P1, D1 | يندرج تحت `OPEN-023` وقرار الخصوصية: كود الخرّيج بيانات شخصية |

**الخلاصة:** التكامل المباشر غير ممكن بواجهة موثّقة. يمكن تقنيًا فقط بإدخال مستودعات الخرّيجين في منظمة GitHub تملكها نَقْلة، بصلاحيات واسعة لا تقبل التجزئة. ووكيلان من الثلاثة (PR Steward، والاعتماد الآلي في Approvals) يخالفان مبادئ نَقْلة الأساسية.

## 3. بناء قدرات مشابهة بـClaude API والوكلاء الحاليين

البنية القائمة تغطي معظم المطلوب **دون وكيل جديد**:

| المطلوب | ما يقابله في نَقْلة |
|---|---|
| مراجعة الكود واكتشاف الأخطاء | **A13** (المقيِّم بنود الرُبريك، ويبقى القرار للمراجِع البشري) و**A03** (الموجّه التقني) |
| شرح الملاحظات وطريق الإصلاح | **A15** (التغذية الراجعة التطويرية، FR-A-010) وقدرة «شرح التقييم» المنفّذة في الحزمة 5 |
| الحكم بالجودة | محرّك التقييم الحتمي، والمراجعة البشرية، وسياسات التحقق القائمة. **لا يُستبدل** |
| البوابة والضوابط | `AgentGateway`: حجب السياق، والسقف، والتحقق من الشكل والمجال، وD-076، ومنع مواد التقييم الخاصة |

ما ينقص فعلًا:
- **(أ)** قراءة كود الخرّيج كنص ملفات مسلَّمة، وهذه موجودة أصلًا في التسليم.
- **(ب)** تشغيل الاختبارات في بيئة معزولة (القسم 4).
- **(ج)** مجموعة تقييم ومعايرة (FR-P-018).

## 4. مراجعة الكود وتشغيل الاختبارات في بيئة معزولة

**قيد قائم:** قرار المالكة 5 ينص على: «لا يُنفَّذ أي كود من مستودع الخرّيج». تشغيل الاختبارات **يغيّر هذا القرار**، فيحتاج موافقتك وتصميمًا أمنيًا قبل أي تنفيذ.

خياران موثّقان في مرجع Claude API (نسخة مخزّنة):

| الخيار | ما هو موثَّق | الملاءمة |
|---|---|---|
| **أداة تنفيذ الكود** (`code_execution`) | حاوية معزولة: 1 معالج، 5 GiB ذاكرة، 5 GiB قرص، **بلا إنترنت**. بايثون 3.11، وأوامر shell. تبقى الحاوية 30 يومًا. 1,550 ساعة مجانية شهريًا للمؤسسة، ثم 0.05$ للساعة | **وجود Node.js غير موثَّق**، وأنشطتنا JavaScript وHTML. يجب التحقق قبل الاعتماد عليها. النموذج هو من يقرر ما يُشغَّل، وهذا لا يناسب تقييمًا يجب أن يكون حتميًا |
| **بيئات Managed Agents** | حاويات على بنية Anthropic بشبكة «محدودة»: منع افتراضي، ومواقع مسموحة صراحة، ومستودعات حزم اختيارية | مناسبة لمشغّل اختبارات **نحدد نحن أوامره**. تحتاج قرار `OPEN-023` |
| **مشغّل معزول تملكه نَقْلة** (حاوية بلا شبكة، بحدود وقت وذاكرة) | لا يعتمد على مزوّد | التحكم الكامل في الحتمية والأمان. يحتاج بنية تشغيل (الحزمة 7) |

**التوصية لتشغيل الاختبارات:**
- اختبارات **نكتبها نحن** لكل نشاط، وهي جزء من مواد المراجِع لا الخرّيج.
- تعمل **حتميًا**: الأوامر ثابتة لا يقررها نموذج، في حاوية **بلا شبكة**، بحدود زمن وذاكرة.
- النتيجة تصبح «فحصًا آليًا» في التقييم، كالفحوص الحتمية القائمة (FR-P-021).
- النموذج **يشرح** النتائج ولا **يقررها**.

## 5. إرشاد الخرّيج ليصلح بنفسه

- **مسموح:** ما يقوله Code Review نفسه: موضع المشكلة، ونوعها، ولماذا تهم.
- **ممنوع:** ما يفعله PR Steward: كتابة الإصلاح.

التصميم المقترح:
1. ملاحظة لكل بند، بالدرجات الثلاث المعروفة: مهم / تحسين / سابق للتغيير، مع **سؤال توجيهي** يقود إلى الإصلاح.
2. تلميحات **تدريجية بطلب الخرّيج**:
   1. أين أنظر؟
   2. ما المفهوم المتعلق؟
   3. مورد تعلّم من السجل (A07).
   - **لا كود جاهز أبدًا.** حارس المخرجات يرفض الكود.
3. محاولة جديدة يقيّمها التقييم نفسه. لا يُحتسب «الإصلاح بمساعدة» تلقائيًا.
4. الإفصاح عن استخدام الذكاء الاصطناعي يبقى كما هو.

## 6. الاعتماد الآلي لجودة الكود وتحويل غير المؤكد للإنسان

**ممكن كاقتراح، لا كقرار نهائي في المرحلة الأولى:**

| الحالة | ما يحدث |
|---|---|
| فحوص حتمية وأخطاء مؤكدة | تُسجَّل آليًا، كما يحدث الآن |
| معيار رُبريك يحتاج حكمًا | يقترح A13 درجة **مع مقتطف داعم ونسبة ثقة** (FR-A-003)، ويقرر المراجِع البشري |
| ثقة منخفضة، أو تعارض بين الفحص والنموذج، أو ملف غير معتاد | **يتحول إلى المراجعة البشرية**؛ طابور المراجعة قائم (FR-A-004) |
| اعتماد آلي كامل لبند | **فقط** بعد معايرة باتفاق ≥ 80% مع الخبير على مجموعة ذهبية (FR-P-018)، وبسياسة معتمدة لكل بند، ومع بقاء العيّنة البشرية |

## 7. الفصل بين اعتماد الكود وإثبات المهارة والجاهزية

ثلاث طبقات منفصلة. هذا الفصل موجود الآن ويبقى:

| الطبقة | ما تعنيه | من يقررها |
|---|---|---|
| **جودة الكود** في تسليم واحد | هذا العمل يستوفي هذه المعايير | التقييم: فحوص حتمية، ومراجِع، ولاحقًا نموذج مُعايَر كاقتراح |
| **إثبات المهارة** | مستوى التحقق من مهارة | سياسة التحقق فقط، من أدلة مُقيَّمة مستقلة. **لا تنتقل جودة كود واحد إلى مستوى تلقائيًا** |
| **الجاهزية المهنية** | استيفاء قواعد دور | محرّك الجاهزية بقواعد معتمدة، ولا يغيّر مستوى أي مهارة |

«اعتماد» Claude Approvals يقع في طبقة **دمج الكود** في مستودع، وهي غير موجودة في نَقْلة أصلًا. لا يجوز أن يُقرأ كاعتماد مهارة ولا كجاهزية.

## 9. الأثر على الوثيقة المرجعية وخطة الوكلاء

**الوكلاء:** **لا وكيل جديد.**
- القدرة تُبنى على A13 (اقتراح مع ثقة)، وA15 (التغذية الراجعة التطويرية)، وA03 (التلميحات التدريجية).
- «وكيل إصلاح» على غرار PR Steward **مرفوض بنيويًا** لأعمال الخرّيجين، لأنه يخالف حظر «تنفيذ المشروع نيابة عنه».

**الوثيقة المرجعية:** لا يلزم تغيير لاستخدام Claude API عبر البوابة: FR-A-003، وFR-A-004، وFR-A-010، وFR-P-018، وFR-P-021 تغطي ذلك. **يلزم طلب تغيير** في حالتين:
- تشغيل كود الخرّيج في بيئة معزولة: يغيّر قرار المالكة 5، ويضيف متطلبًا أمنيًا غير وظيفي للعزل؛
- أي استخدام لـClaude Ship نفسه: يضيف مزوّدًا خارجيًا، ومنظمة GitHub، وصلاحيات، وبيانات تخرج إلى طرف ثالث (`OPEN-023`).

**الاستخدام الداخلي المقبول:** يمكن استخدام Claude Ship **لمراجعة كود منصة نَقْلة نفسها**، في مستودع الفريق، لا أعمال الخرّيجين. هذا قرار هندسي داخلي منفصل يحتاج خطة Team أو Enterprise.

## 10. التوصية النهائية

1. **لا تكامل مباشر** لـClaude Ship مع أعمال الخرّيجين. لا واجهة موثّقة لذلك؛ صلاحياته واسعة ولا تتجزأ؛ PR Steward يكتب الحل؛ والاعتماد قد يتم بلا إنسان.
2. **بناء القدرة داخل نَقْلة** على البوابة والعقود القائمة (A13، A15، A03) باستخدام Claude API، على مراحل:
   - **R1 (الآن، مزوّد الاختبار):** عقد «اقتراح ملاحظة لكل بند بدرجة خطورة ومقتطف وثقة»، وحارس يمنع الكود الجاهز، وتلميحات تدريجية، واختبارات.
   - **R2 (بعد موافقتك وتصميم أمني):** مشغّل اختبارات حتمي معزول، باختبارات يكتبها الفريق، تصبح فحصًا آليًا.
   - **R3 (بعد `OPEN-023`):** نموذج حقيقي للشرح والاقتراح، ومعايرة على مجموعة ذهبية، ثم اعتماد آلي لبنود محددة فقط بعد اتفاق ≥ 80%، ومع عيّنة بشرية دائمة.
3. **اختياري ومنفصل:** تجربة Code Review على مستودع نَقْلة الداخلي لتحسين جودة المنصة، بقرار تكلفة مستقل.

## 11. تصور تجربة الخرّيج

1. يعمل في مستودعه الخاص، كما في القرار 5، ويسلّم رابط طلب الدمج ورمز آخر إيداع، مع ملفاته.
2. خلال دقائق يرى في صفحة التقييم:
   - **«فحوص آلية»:** نتيجة اختبارات النشاط الحتمية (بعد R2): ما نجح وما فشل، دون إظهار الاختبار المخفي نفسه؛
   - **«ملاحظات على الكود»:** لكل بند موضع ونوع (مهم / تحسين) وسؤال توجيهي، مع وسم دائم: «اقتراح آلي، ولم يقرر المستوى».
3. يضغط «أعطني تلميحًا» عند ملاحظة: التلميح الأول «أين أنظر»، ثم «المفهوم»، ثم «مورد تعلّم». **لا كود.**
4. يصلح بنفسه ويرسل محاولة جديدة؛ يقيّمها التقييم نفسه.
5. البنود غير المؤكدة تظهر «قيد المراجعة البشرية». المراجِع يرى الاقتراح والمقتطف ونسبة الثقة، ويقرر.
6. المستوى لا يتغير إلا بسياسة التحقق من أدلة مُقيَّمة. **«الكود جيد» لا يعني «المهارة مثبتة»**، والجاهزية تقرير منفصل.
