# B. المهارات الأساسية الخمس
«أساسية» صفة على **ربط الدور**، لا على المهارة نفسها. كل واحدة أدناه: لماذا، ماذا نلاحظ، كيف تُثبَت، وما ينقص. **`Verified` محجوب للخمس** — لا نشاط تحقق ولا سياسة (D-059؛ قرار إطلاق منفصل)، وهذا واقع المنصّة لا عيب في الحزمة.

## B1 · بنية HTML الدلالية — Semantic HTML & document structure 🟡
- **لماذا أساسية:** بنية الصفحة هي ما تُبنى عليه الإتاحة والتنسيق والاختبار.
- **المؤشرات الملاحَظة:** ترتيب عناوين منطقي · landmarks (header/nav/main/footer) · نموذج من form/label/button لا من div.
- **مسار الدليل الحالي:** ملف HTML في نشاطين. **الأنشطة:** بناء الواجهة (عمق أساسي) · التصحيح والتحسين (عمق أساسي). **المعايير:** «بنية دلالية» (إلزامي) · «البنية الدلالية أُصلحت» (إلزامي).
- **Demonstrated قابل للبلوغ:** نعم (نشاطان). **Verified:** محجوب.
- **توصية المالكة (مقترحة):** إبقاؤها أساسية؛ عرضها على SME كما هي.
- **سؤال SME:** هل الاسم العربي هو مصطلح السوق؟ هل المؤشرات الثلاثة تكفي لتمييز مستوى `working`؟
- **حاجب الاعتماد:** لقطة معيار HTML الرسمي وترخيصه (OPEN-042).

## B2 · تنسيق CSS والتصميم المتجاوب — CSS layout & responsive design 🟡
- **لماذا:** معظم الاستخدام من الجوال؛ صفحة لا تتجاوب لا تُستخدم.
- **المؤشرات:** التخطيط يصمد عند 360px و1024px · لا تمرير أفقي غير مقصود · وحدات نسبية حيث يلزم.
- **مسار الدليل:** ملف CSS. **الأنشطة:** بناء الواجهة (**ثانوي**) · التصحيح والتحسين (أساسي). **المعايير:** «تخطيط متجاوب» (**اختياري**) · «السلوك المتجاوب أُصلح» (إلزامي).
- **Demonstrated:** نعم. **Verified:** محجوب.
- **⚠ تغطية ضحلة:** معيار إلزامي واحد فعلي؛ الثاني اختياري وفي نشاط تقيسها ثانويًا. لا تُضخَّم الأوزان لتعويض ذلك.
- **توصية المالكة:** إبقاؤها أساسية؛ السؤال البنيوي لـSME: هل يصير «تخطيط متجاوب» إلزاميًا في نشاط البناء؟
- **سؤال SME:** هل 360/1024 العرضان المناسبان محليًا؟ هل ذكر Flexbox/Grid في التعريف مقبول لمسار عام؟
- **حاجب الاعتماد:** لقطة مواصفات CSS (W3C).

## B3 · أساسيات JavaScript — JavaScript fundamentals 🟡
- **لماذا:** كل تفاعل وكل جلب بيانات يمر بـJavaScript صحيح.
- **المؤشرات:** يميّز المرجع من القيمة · async/await مع معالجة الرفض · لا متغيرات عامة عرَضية.
- **مسار الدليل:** ملف JS. **الأنشطة:** التصحيح والتحسين (أساسي) · طلب التغيير (أساسي). **المعايير:** «التحقق وحالات الخطأ أُصلحت» (إلزامي — **يقيس التحقق من النماذج أكثر من JS**) · «صحة JavaScript» (إلزامي).
- **Demonstrated:** نعم. **Verified:** محجوب.
- **⚠ تغطية ضحلة + سؤال ربط:** التغطية الصادقة معيار واحد؛ الثاني قد ينتمي إلى مهارة النماذج. ربط الدور يتوقَّع **دفاعًا حيًا** لا يوفّره أي نشاط (OD-10).
- **توصية المالكة:** إبقاؤها أساسية؛ حذف توقُّع الدفاع الحي من الإصدار الأول (OD-10).
- **سؤال SME:** «يميّز المرجع من القيمة» — ملاحَظ في كود، أم يحتاج حوارًا؟ هل يُربط معيار التحقق بالنماذج بدل JS؟
- **حاجب الاعتماد:** لقطة ECMA-262.

## B4 · إدارة حالة الواجهة والتفاعل — UI state & interaction handling 🟢
- **لماذا:** أشيع أعطال المبتدئ حالات متناقضة أو مفقودة.
- **المؤشرات:** لكل حالة ظاهرة تمثيل واحد · التفاعل يغيّر الحالة والعرض يتبعها · لا تعارض بين المعروض والمخزَّن.
- **مسار الدليل:** ملف JS + السلوك. **الأنشطة:** بناء الواجهة (أساسي) · طلب التغيير (أساسي). **المعايير:** «انتقالات الحالة» (إلزامي) · «التصفية عبر الحالة» (إلزامي) + ملاحظتان يراها المراجع («التصفية في الحالة لا في DOM»).
- **Demonstrated:** نعم. **Verified:** محجوب.
- **الكانونية بعد OPEN-039:** هذه هي المهارة الكانونية؛ «إدارة حالة الواجهة» من الشريحة الأولى مرادفها المكافئ (بقي صفّها ومعرّفها وتاريخها).
- **توصية المالكة:** كما هي.
- **سؤال SME:** هل تتداخل مع B5 (حالات البيانات جزء من حالة الواجهة)؟ إن نعم، أيهما تبقى أساسية؟
- **المصدر:** ممارسة لا معيار — حكم SME هو المصدر (غير حاجب).

## B5 · جلب بيانات API ومعالجة حالاتها — Fetching API data & handling its states 🟢
- **لماذا:** واجهة بلا بيانات حقيقية ليست منتجًا؛ التحميل والخطأ والفراغ هي الفرق بين نموذج وواجهة.
- **المؤشرات:** حالة تحميل ظاهرة · رسالة خطأ يفهمها المستخدم · الاستجابة الفارغة حالة لا انهيار.
- **مسار الدليل:** JS + السلوك. **الأنشطة:** بناء الواجهة (أساسي) · طلب التغيير (أساسي). **المعايير:** «حالات البيانات» (إلزامي) · «الحالة الفارغة صحيحة» (إلزامي) + ٣ ملاحظات للمراجع (استجابة `[]` · فشل 500 · فراغ بعد التصفية).
- **Demonstrated:** نعم. **Verified:** محجوب.
- **توصية المالكة:** كما هي.
- **سؤال SME:** هل يكفي `fetch` المعياري أم يتوقَّع السوق مكتبة (لا تُسمَّى)؟
- **المصدر:** ممارسة — حكم SME.

**قرار المالكة على القسم:** OD-2 (المجموعة مغلقة للمراجعة).

# E. الأنشطة الثلاثة
كل نشاط: مدخل خاص بالمنصّة · عطل مزروع · سؤال شرح · بمساعد AI مسموح **ومُعلَن** (الإفصاح لا يخفض الدرجة) · يقترح `demonstrated` عند الاجتياز · **لا يمنح `verified`**.

## E1 · بناء واجهة تفاعلية بمدخلات مُهيكلة وحالات بيانات (120 دقيقة ⚪)
- **الغرض:** قياس حالة الواجهة وحالات البيانات والبنية الدلالية معًا في مخرَج واحد.
- **السيناريو:** فريق منتج صغير يريد صفحة «طلب إجازة»: نموذج أربعة حقول + قائمة الطلبات السابقة من خدمة داخلية. القرار المعلَّق: هل تصلح لتجربة ٢٠ موظفًا الأسبوع القادم؟ الوصف يقول أربعة حقول وقائمة الحقول تذكر خمسة (تعارض مقصود).
- **المخرجات الإلزامية:** HTML · CSS · JS · ملاحظة تدفق البيانات (فقرة) · إجابة سؤال الاستيضاح.
- **المهارات المقاسة بعمق (أساسية):** حالة الواجهة · حالات البيانات · HTML الدلالية. **مساندة:** CSS · نماذج · شرح.
- **الفحوص الحتمية:** الملفات الثلاثة موجودة (**حاجب**) · إجابة الاستيضاح ≥ 40 حرفًا · ملاحظة التدفق ≥ 80 حرفًا · معيار «اكتمال المخرجات» (بوابة).
- **بنود المراجعة البشرية (٧):** بنية دلالية · تحقق النموذج · حالات البيانات · انتقالات الحالة · تخطيط متجاوب · وضوح الشرح · فحص الافتراض.
- **فحوص النزاهة:** ٥ نشطة (٣ حتمية + ٢ يلاحظها المراجع: استجابة `[]` · فشل 500 → تُعرض لمراجع «حالات البيانات») · **حُذف** فحص «عدد الحقول المزروع» لتكراره مع سؤال الاستيضاح ومعيار الافتراض.
- **الرُبريك:** `rub_fe_build_interface` · عتبة 0.75 (proposed) · ٨ بنود.
- **ما يمكن أن يُنتجه من دليل:** `demonstrated` للمهارات التي تجاوزت بنودها العتبة.
- **ما لا يُثبته:** التجاوب الفعلي في متصفح (لا مُشغِّل عرض) · العمل تحت ضغط الوقت (المدة تقدير) · أي `verified`.
- **مخاطر معروفة:** تعارض ٤/٥ حقول قد يُقرأ لغمًا لا سؤال مالك منتج · خمسة مخرجات في 120 دقيقة.
- **قرار المالكة:** OD-6 · **سؤال SME:** هل التعارض عادل؟ هل 120 دقيقة كافية مع مساعد AI؟ بدونه؟

## E2 · تصحيح وتحسين تنفيذ واجهة قائم (90 دقيقة ⚪)
- **الغرض:** قياس CSS وHTML وJS **إصلاحًا لا بناءً** مع انضباط بالنطاق.
- **السيناريو:** صفحة «تسجيل ورشة» عليها شكاوى: تنكسر على الجوال، لا تُستخدم بلوحة المفاتيح، تقبل بريدًا غير صالح؛ التسويق يريدها خلال يومين. أربعة أعطال مزروعة، وشكوى تصف عرَضًا لا سببًا («الزر لا يعمل»).
- **المخرجات الإلزامية:** الملفات الثلاثة بعد الإصلاح · ملاحظة الأسباب الجذرية (سطر لكل عطل) · إجابة سؤال الشرح.
- **المهارات المقاسة بعمق:** CSS · HTML · JS. **مساندة:** إتاحة · نماذج · تصحيح.
- **الفحوص الحتمية:** الملفات (**حاجب**) · إجابة الشرح ≥ 60 حرفًا · بوابة الاكتمال (تشمل الملاحظة).
- **بنود المراجعة البشرية (٦):** التجاوب أُصلح · الدلالية أُصلحت · أساسيات الإتاحة أُصلحت · التحقق والأخطاء أُصلحت · ملاحظة السبب الجذري · الانضباط بالنطاق.
- **فحوص النزاهة:** ٢ حتمية + ٢ يلاحظها المراجع (`overflow-x: hidden` قناع → لمراجع «التجاوب» · تحقق البريد → لمراجع «التحقق») + **٢ مؤجَّلان معطَّلان** (تعديل لاحق 900px يحتاج جولة متابعة · اتساق التخطيط عند عرضَين يحتاج مُشغِّل متصفح).
- **الرُبريك:** `rub_fe_debug_improve` · 0.75 (proposed) · ٧ بنود.
- **ما لا يُثبته:** التخطيط الفعلي عند العرضَين (يُقرأ من CSS فقط) · الاستجابة لتعديل لاحق.
- **مخاطر:** «الانضباط بالنطاق» يحتاج رؤية الفرق (diff) والمراجع يرى الملفات النهائية فقط · «مُقنَّع» كمستوى وسطي قد يُقرأ نصف نجاح.
- **قرار المالكة:** OD-6 · **سؤال SME:** هل الأعطال الأربعة شكاوى حقيقية؟ هل الشكوى-العرَض واضحة لمبتدئ؟

## E3 · تعديل مشروع قائم بعد تغيّر المتطلب (90 دقيقة ⚪)
- **الغرض:** قياس JS وحالة الواجهة وحالات البيانات **داخل كود لم يكتبه** مع شرح قرار.
- **السيناريو:** قائمة «مهام الفريق» تعمل منذ شهر. المطلوب: (١) تصفية بالحالة، (٢) إصلاح بلاغ «القائمة الفارغة تعرض خطأً». داخل المشروع نفسه، لا مشروع جديد.
- **المخرجات الإلزامية:** السكربت المعدَّل · ملاحظة القرار (السبب الجذري · ما تغيّر · البديل المرفوض) · إجابة سؤال الشرح (+الصفحة إن تغيّرت).
- **المهارات المقاسة بعمق:** JS · حالة الواجهة · حالات البيانات. **مساندة:** قراءة كود · تصحيح · شرح.
- **الفحوص الحتمية:** السكربت + الملاحظة (**حاجب**) · إجابة الشرح ≥ 60 · بوابة الاكتمال.
- **بنود المراجعة البشرية (٦):** السبب الجذري أُصلح · التصفية عبر الحالة · صحة JavaScript · الحالة الفارغة صحيحة · فهم الكود القائم · القرار مشروح بالبديل.
- **فحوص النزاهة:** ٢ حتمية + ٣ يلاحظها المراجع (`[]` كخطأ → «السبب الجذري» · التصفية في الحالة → «التصفية عبر الحالة» · فراغ بعد التصفية → «الحالة الفارغة») + **١ مؤجَّل معطَّل** (تصفية ثانية بعد التسليم).
- **الرُبريك:** `rub_fe_change_request` · 0.75 (proposed) · ٧ بنود.
- **ما لا يُثبته:** الاستجابة لطلب متابعة · أن المشروع «قائم منذ شهر» بحجم واقعي (ملف حالة واحد).
- **مخاطر:** «البديل المرفوض» قد يدفع المبتدئ لاختراع بديل (§K).
- **قرار المالكة:** OD-6 · **سؤال SME:** هل `[]` كخطأ عطل واقعي في كود قائم؟ هل سؤال البديل عادل لمبتدئ؟

# L. تدقيق «لا React» (§9)
| الادعاء | كيف تحقّقنا | النتيجة |
