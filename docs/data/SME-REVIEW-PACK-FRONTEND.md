# حزمة مراجعة SME — Junior Web / Frontend Developer
**المطلوب من المراجع/ة (R-3):** قرار مكتوب لكل بند أدناه. **لا شيء في هذه الحزمة معتمد**؛ كل صف `draft` وكل مراجعة تُسجَّل بأمر `review` بالاسم والسبب والزمن.

## كيف تُراجَع
```
# 1 · انقل السجل إلى curated (مؤلف المحتوى) بعد التأكد من اكتمال الحقول
node scripts/career-data.mjs review skill <uuid> curated --role content_author --by - --label "<name>" --reason "fields complete"
# 2 · مراجعة SME (باسم وهوية)
node scripts/career-data.mjs review skill <uuid> sme_reviewed --role sme --by <reviewer-uuid> --label "<name>" --reason "<what was checked>" --minutes 12
node scripts/career-data.mjs review skill <uuid> approved     --role sme --by <reviewer-uuid> --label "<name>" --reason "<why>"
# 3 · النشر (مالكة المنتج) — يتطلب approved
node scripts/career-data.mjs review skill <uuid> published --role product_owner --by - --label "R-1" --reason "pack 0.1.0 publish"
```
**تنبيه:** حزمة `trk_frontend_junior@0.1.0` موسومة **DEMO**؛ الأوامر أعلاه **ترفض** `sme_reviewed`/`approved` لصف demo. الاعتماد الحقيقي يبدأ بإعادة استيراد الحزمة بوصفها محتوى حقيقيًا (`is_demo_fixture=false` في المانيفست) بعد قرار المالكة (`OPEN-040`).

## أ. قرارات الدور
| # | السؤال | القرار |
|---|---|---|
| A1 | هل الوصف صادق لما يُطلب من مبتدئ في سوق العمل السعودي؟ | |
| A2 | «ما لا يُتوقَّع من المبتدئ» — هل تنقص/تزيد عناصر؟ | |

| A4 | هل يجب أن يسمّي الدور **أي** إطار عمل؟ (توصية: لا — يبقى عامًا) | |

## ب. المهارات الأساسية (٥) — تأكيد أو استبدال
| المهارة | لماذا أساسية (مقترح) | مؤشرات ملاحَظة (مقترحة) | القرار |
|---|---|---|---|
| Semantic HTML | البنية أساس الإتاحة والتنسيق والاختبار | ترتيب عناوين · landmarks · نموذج بعناصر form/label | |
| CSS responsive | معظم الاستخدام جوال | يصمد عند 360/1024 · لا تمرير أفقي | |
| JavaScript fundamentals | كل تفاعل وجلب يمر به | async مع معالجة الرفض · لا متغيرات عامة عرَضية | |
| UI state & interaction | أشيع أعطال المبتدئ | حالة صريحة · العرض يتبعها | |
| API data & states | الفرق بين نموذج وواجهة | تحميل/خطأ/فراغ ظاهرة | |
**سؤال مفتوح للمراجع:** هل تُدمج `skl_ui_state_interaction` مع مهارة الشريحة ١ `ui-state-management` (تشابه 0.9 بالعربية — تقرير التكرار)؟ خيارات: دمج (`merged_into`) · إبقاء منفصلتين مع علاقة `related` (الحالي) · إعادة تسمية.

## ج. المهارات المساندة (٨) — ملاءمة المستوى المستهدف
لكل منها `target_proficiency` مقترح (`working` أو `foundation`) و`why_required`. المطلوب: تأكيد المستوى، وهل `ui-testing` تبقى في ربط الدور رغم أن **لا نشاط ولا مهمة تقيسها** (تحذير Q18).

## د. المهام (١١) — الواقعية وأنماط الفشل
لكل مهمة: هل المخرَج ملموس؟ هل `common_failure_modes` هي ما يفعله المبتدئ فعلًا؟ (أنماط الفشل هي مادة فحوص النزاهة.) أضيفي ما ينقص.

## هـ. الأنشطة (٣) وفحوص النزاهة (١٨)
| النشاط | أسئلة المراجعة |
|---|---|
| build_interface | هل ١٢٠ دقيقة واقعية؟ هل تناقض «٤ حقول / ٥ حقول» عادل أم مُلغَّم؟ هل سؤال الاستيضاح يُفهم كجزء من العمل لا كفحص غش؟ |
| debug_improve | هل الأعطال الأربعة المزروعة تمثّل شكاوى حقيقية؟ هل «التعديل اللاحق» (900px) يقيس الفهم أم الطاعة؟ |
| change_request | هل «البديل المرفوض» سؤال يجيب عنه مبتدئ بصدق؟ هل `[]` كخطأ مزروع واقعي؟ |
**قاعدة:** التجربة يجب أن تبدو **فهمًا واستقلالًا** لا كشف تحايل. الفحوص assessment-only لا تظهر للمستخدم أبدًا (قيد قاعدة).

## و. الرُبريكات (٣ · ٢٢ بندًا)
لكل بند: هل الواصفات (unmet/met أو missing/partial/solid) تميّز فعلًا؟ هل `threshold_for_skill = 0.5` مناسب؟ هل الوزن متناسب؟ هل البند مرتبط بالمهارة الصحيحة؟ **٧ بنود من المكتبة العامة** — هل صياغتها العامة تصلح لهذا المسار؟

## ز. ما تطلبه المنصّة من SME صراحةً (لا يُؤتمَت)
1. اعتماد تسمية المهارات العربية (المصطلح المستخدم في السوق لا الترجمة).
2. القرار في التكرار `ui-state-management` / `skl_ui_state_interaction`.
3. اعتماد العتبات (0.75) والأوزان — الآن قيم افتراضية للمعايرة.
4. سياسة الحداثة (نوافذ الأشهر) — للمعايرة (D-023).
5. أي نشاط يطمح إلى `Verified` لاحقًا: I1+I2+I3 موجودة في التصميم، **لكن سياسة التحقق غير موجودة**.

## ح. ما يُقاس أثناء المراجعة (D-030 · D-038)
`--minutes` في كل أمر مراجعة يُسجَّل في `review_log.duration_minutes`؛ تعارض المصالح `--conflict` إن كان المراجع هو المؤلف.
